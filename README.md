專案名稱：AIoT 智慧電視邊緣中控台
GitHub Repository: AIoT-Smart-TV-controller

一、 設計理念與產業痛點 
產業痛點：
在當前智慧家庭與物聯網（IoT）場域中，雲端化往往伴隨著高延遲、隱私外洩風險以及依賴外部伺服器穩定性的隱患。
此外，傳統網頁前端受限於瀏覽器安全沙箱（Sandbox），無法直接發送底層網路通訊協定（如 UDP 廣播或 Wake-on-LAN 喚醒封包），
導致「網頁介面」與「實體硬體設備」之間常出現斷層。

設計理念：
本專案旨在建構一套「雲端展示與邊緣實作並重」的輕量化 AIoT 中控台。
前端採用柔和舒適的現代化淺灰藍色系（Soft Slate/Ice Blue）儀表板設計，兼具高識別度與長時間操作的視覺舒適感；
架構上則透過「本地中繼伺服器（Local Relay Server）」打通前端介面與區域網路硬體設備的資料鏈路，實現直覺、高效率的智慧裝置狀態機控制。

二、 核心使用技術 
前端展示層 ：
HTML5 / JavaScript (ES6+)：實現非同步請求 (fetch API)、動態狀態機管理、即時時鐘與事件時序日誌互動渲染。

CSS：運用現代化原子級 CSS 框架，打造符合工業級儀表板美學的溫潤淺色系響應式介面。

後端與通訊層 (Backend & API)：

Python：運用原生輕量化架構（http.server 與 socket 模組），不需依賴第三方套件，兼具高效能與低資源耗損。

RESTful API / CORS：設計 /wake-tv 本地中繼端點，並完整配置跨域標頭，無縫對接前端與硬體指令傳遞。

物聯網通訊協定：

UDP Socket / Broadcast：透過區域網路的「廣播」特性，將電視的硬體編號（MAC 位址）包裝成一組特定的喚醒指令（魔法封包），
直接在區網內發送，讓遠端設備接收到訊號後自動從待機狀態被喚醒。

三、 遇到的挑戰與突破解法
挑戰一：瀏覽器沙箱限制與硬體通訊的鴻溝

問題描述：前端網頁基於資安考量，無法直接呼叫作業系統層級的 UDP 通訊埠發送區域網路喚醒指令。

解決方案：設計「輕量化本地中繼架構」。由 Python 建立極速 HTTP 伺服器接收前端請求，再由後端程式代為向區網廣播 UDP 封包，成功在「網頁互動」與「底層硬體控制」之間建立穩固的通訊橋樑。

挑戰二：Windows 作業系統環境路徑與直譯器劫持

問題描述：初期的命令列執行常因 Windows Store 空白捷徑或環境變數污染，導致直譯器靜默退出或指令失效。

解決方案：排除系統路徑劫持後，全面優化標準 Python 執行環境配置，確保背景常駐監聽程序（Port 3000）穩定運行，並在終端機提供即時回饋日誌。

挑戰三：雲端展示與實機連線的適應性

問題描述：當專案部署至 GitHub Pages 進行雲端展示時，外部評審無法直接連線至開發者的區域網路實機；此外，Wi-Fi 設備在待機時常因硬體省電策略自動斷開無線網卡電源。

解決方案：在前端導入「雙模狀態機（Dual-mode State Machine）」。當偵測不到本地伺服器時，系統會自動無縫切換為「高擬真模擬模式」，並
於時序紀錄（Time-series Log）中即時呈現完整的控制反饋與日誌，兼顧了「實機聯網操作」與「公開雲端展示」的完美流暢度。
